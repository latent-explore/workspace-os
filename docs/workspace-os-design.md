# Workspace OS: Design

A personal system where agents work 24/7 on one always-on Linux machine. I steer; agents execute.

It manages the workspaces I already have, plus new ones, without moving anything.

## Goals

- **Limited by tokens, not by work.** Agents always have a queue.
- **Short, human-style updates.** No walls of text.
- **Few decisions per day**, batched and with a recommendation.
- **Agents get better** from every run.
- **Every new workspace starts with what earlier workspaces learned.**
- **Clean code, no slop.**
- **Later:** let other people use my agents, under my control.

## Principles

1. **Battle-tested and free tools only.** The only cost is Claude tokens.
2. **Build the smallest working version first.** Add a part only when something hurts.
3. **Keep the glue thin.** A small dispatcher I own, not a framework.
4. **Run logs are the foundation.** Monitoring, reports and learning all read them.
5. **Every agent change is a PR.** I approve. Nothing is deleted directly.
6. **Git everything.** Anything can be recovered.
7. **Don't move existing work.** Register it where it is.
8. **Channels are not workflows.** Slack, Telegram and the terminal are just pipes; the workflow behind them is the same.

## Layers

| # | Layer | Job |
|---|---|---|
| 1 | Workspace | Folder holding a workspace's repos, instructions and docs |
| 2 | Agent | Claude Code + prompt + context |
| 3 | Orchestration | Starts agents, feeds context, handles handoffs, retries and schedules |
| 4 | Project management | What to do, in what order, and what is done |
| 5 | Interaction | How I talk to the system |

## Component map

**Where work lives**

| Generic name | Tool | Responsibility |
|---|---|---|
| **Host** | Always-on Linux machine | Runs everything 24/7 |
| **Workspace OS** | `~/workspace-os/` (plain folder) | Home for the system repos and new workspaces |
| **Registry** | `system/workspaces.yaml` | Source of truth: every workspace's path, repo and channel |
| **Base Workspace** | `ws-base` repo | Workspace template, shared skills, account-wide decisions |
| **Shared Skill Pack** | Claude Code plugin in `ws-base` | Generic skills and agents, installed into every workspace |
| **Workspace** | Folder + its own `ws-<name>` repo | Holds a project's repos, instructions, agents and docs |
| **Task Branch** | Git branch | One per task, same name in every repo it touches. Deleted after merge |
| **Task Worktree** | Git worktree in `.worktrees/<task>/` | Separate checkout for each task, so tasks run in parallel without clashing |
| **Setup Skill** | `workspace-os` skill in the Shared Skill Pack | Sets up the system; creates and onboards workspaces |

**Doing the work**

| Generic name | Tool | Responsibility |
|---|---|---|
| **Agent Runtime** | Claude Code, headless (`claude -p`) | Does the work inside a workspace |
| **Lead** | Planner agent, one per workspace | The agent I talk to. Turns ideas into plans, picks the deliverable type, hands work to the team |
| **Agent Team** | `.claude/agents/` per workspace | Roles specific to the workspace. Work behind the Lead |
| **HQ Agent** | Lead for the whole system, runs in `ws-index` | Answers questions across workspaces; routes work to the right one |
| **Dispatcher** | Small Python service in `ws-system` | Picks tasks, builds context, manages worktrees, starts agents, caps how many run at once, retries, pauses at rate limits |
| **Scheduler** | Part of `ws-system`, wakes every minute | Runs the Schedule List; hands due entries to the Dispatcher |
| **Schedule List** | `schedules.yaml` (system) + Postgres (agent-made) | Every timed job: what, when, who made it, until when |
| **Supervisor** | systemd + tmux | Keeps services alive and restarts them after crashes or reboots |
| **Sandbox** | Dedicated Linux user, later containers | Limits each agent's files, CPU, RAM and disk |
| **Secrets Vault** | `~/.config/workspace-os/env` | Narrowly scoped tokens, kept outside every repo |

**Tracking**

| Generic name | Tool | Responsibility |
|---|---|---|
| **Task Tracker** | GitHub Issues | Plans, task queue and audit trail |
| **Portfolio Board** | GitHub Projects (spans all repos) | Status of every workspace in one view |
| **Review Gate** | GitHub PRs | Every change, including agent self-improvements, passes my approval here |
| **Automation Runner** | GitHub Actions on a self-hosted runner | CI, deploys, site builds. Uses no paid minutes |

**Interaction and monitoring**

| Generic name | Tool | Responsibility |
|---|---|---|
| **Pratik Interaction Surface** | Slack (my own free workspace) | Where I talk to the system |
| **Relay** | Slack bot (Socket Mode) in `ws-system/relay/` | Plain code, not an agent. Carries my messages to Claude sessions and posts replies, cards and reports back |
| **Reports** | Generated by agents | Daily brief and Weekly Review |
| **Run Store** | Claude Code session logs + Postgres | Raw logs per run, plus one summary row per run |
| **Monitoring Console** | Grafana | Index of metrics with drill-down to single runs |
| **Secure Gateway** | Cloudflare Tunnel + Access, or Tailscale | Reach the Monitoring Console from anywhere, behind a login |
| **Showcase Site** | GitHub Pages (Jekyll or Hugo) | Public site for my best work |

**Memory**

| Generic name | Tool | Responsibility |
|---|---|---|
| **Workspace Docs** | `docs/` in each workspace | `ROADMAP.md`, `LOG.md`, `wiki/` |
| **Global Index** | `ws-index` repo + Postgres | Dated index of everything; answers "what did Pratik do this year?" |

**Background agents**

| Generic name | Tool | Responsibility |
|---|---|---|
| **Planner (scheduled)** | The Lead, run daily | Proposes new tasks from the roadmap when the queue runs low |
| **Improver** | Agent, one per workspace, daily | Studies runs, finds failure patterns, proposes better skills, agent files and docs |
| **Code Reviewer** | Agent | Reviews every PR before I see it |
| **Housekeeper** | One nightly agent with several jobs | Updates the Global Index; removes duplicates, dead code and stale docs (as PRs) |

**Constraint**

| Generic name | Tool | Responsibility |
|---|---|---|
| **Token Budget** | Claude plan limits | The real bottleneck. Tracked and split by job type |

**Repos**

| Type | Repos | Count |
|---|---|---|
| System | `ws-base`, `ws-system`, `ws-index` | 3 |
| Workspace repos | `ws-invoicer`, `ws-llm-evals`, `ws-acme`, `ws-showcase` | 4 |
| Repos inside workspaces | `invoicer-api`, `invoicer-web`, `invoicer-infra`, `llm-evals-harness`, `llm-evals-paper`, `<you>.github.io` | 6 |
| Client-owned (cloned) | `acme-org/acme-app` | 1 |

**Rules**
- `workspace-os/` is a plain folder, not a repo. Workspaces may live anywhere; the Registry knows where.
- Each workspace repo tracks the agent setup and knowledge for that workspace. The work itself lives in the repos inside it.
- Each workspace's `.gitignore` excludes the repos inside it. No submodules.
- Repos sit at the root of their workspace.
- Naming: `ws-` marks system and workspace repos; repos inside a workspace are prefixed with the workspace name.
- Everything is private except `<you>.github.io`.

## Registry

One entry per workspace: where it is on this machine, where it lives on GitHub, and its Slack channel.

```yaml
# system/workspaces.yaml
invoicer:
  path: ~/workspace-os/invoicer
  repo: github.com/<you>/ws-invoicer
  channel: "#invoicer"
llm-evals:
  path: ~/research/llm-evals
  repo: github.com/<you>/ws-llm-evals
  channel: "#llm-evals"
```

Each workspace lists its own repos in `repos.yaml`:

```yaml
# invoicer/repos.yaml
api:   github.com/<you>/invoicer-api
web:   github.com/<you>/invoicer-web
infra: github.com/<you>/invoicer-infra
```

**Why the split:** each fact lives in one place. The Registry knows where workspaces are; each workspace knows its own repos.

**What the repo links give us:**
- **Rebuild the machine** from `ws-system` alone: Registry → clone the workspaces → `repos.yaml` → clone their repos.
- **The Global Index and Reports** can read GitHub activity for each workspace.
- **The Dispatcher** knows which Task Tracker belongs to each workspace.

## Interaction

**Slack maps onto the system**

| Slack | Workspace OS |
|---|---|
| My Slack workspace | This copy of Workspace OS |
| `#hq` | HQ Agent + overall reports |
| `#<workspace>` channel | One workspace |
| New message in a channel | New conversation = new Claude session in that workspace |
| Replies in its thread | Same session continues |
| DM from the bot | Only things that need me now |

```
#hq                          ← questions about everything; daily brief, weekly review
#invoicer
├── 📊 Reports               ← invoicer's daily and weekly updates
├── ✅ Add billing export    ← conversation (thread)
└── 🔨 Why is login slow?    ← conversation (thread)
#llm-evals
└── ⏳ Run evals on new model
DM                           ← "Decision needed", "Run failed"
```

**Who I talk to**
- **About one workspace:** its Lead, in that workspace's channel.
- **About everything, or not sure where:** the HQ Agent, in `#hq`. It can open a thread in the right workspace for me.
- I never talk to Agent Team members directly.

**How the Lead talks** (set in its agent file)
- At most 5 lines, like a person would.
- One question at a time.
- Anything long goes in a file or issue, with a link.

**The Relay**
- Plain code, not an agent, so it uses no tokens.
- **In:** my message → the right workspace (from the channel) → the right session (from the thread).
- **Out:** replies, plans, status updates, delivery cards, reports, alerts.
- Thread ↔ session mapping is kept in Postgres; the GitHub issue links to its thread.
- **Only the Relay knows about Slack.** The rest of the system sees messages in and cards out.

**Slack MCP:** optional. Lets agents read and post in Slack, such as rereading a long thread. It can't wake the system up when I post; that's the Relay's job.

**Telegram works too** (only the Relay's connection changes)

| Slack | Telegram |
|---|---|
| Channel | A group with Topics turned on |
| Thread | Topic (start one with `/new <idea>` in General) |
| `#hq` | An "HQ" group |
| DM | A private chat with the bot |

Slack fits better: channels and threads map cleanly, and search and history are stronger.

## Task pipeline

```
Idea → Plan → Brief → Team run → Deliverable → Delivery
```

| Step | What happens | Who |
|---|---|---|
| **Idea** | A one-line request in a channel | Me, or the scheduled Planner |
| **Plan** | An issue with: goal, **deliverable type**, "done when", steps, repos, merge order | Lead |
| **Brief** | The prompt for the team: plan + workspace `CLAUDE.md` + relevant docs | Dispatcher |
| **Team run** | The work. Handoffs go through files on the task branch and issue comments, not agent memory, so a crash loses nothing | Agent Team |
| **Deliverable** | One of a fixed set of types | Agent Team |
| **Delivery** | A short card in the thread | Relay |

**Deliverable types** (chosen at the Plan step; they decide the team, the "done" check and what I get)

| Type | Done when | I get |
|---|---|---|
| **PR** | Tests pass and the review is clean | Link + 3-line summary |
| **Experiment** | All runs finish (watched through the Scheduler) | Results table + a recommendation |
| **Answer** | A report file is written | 5-line answer + link to the full report |

**Approving a plan**
1. The Lead writes the full plan into the GitHub issue.
2. In the thread: a 3-line summary, a link, and **[Approve] [Change] [Discuss]**.
3. I tap **Approve**, or reply "go". For changes, I reply in plain words.

**Tracking a deliverable**
- The thread is the task's timeline.
- One status message is edited as the task moves on: ⏳ planning → 🔨 building → 👀 review → ✅ done.
- An emoji on the thread's first message shows its status, so the channel can be scanned at a glance.
- The final message is the delivery card: result, link, any decision needed.
- Across all workspaces: the Monitoring Console and the Portfolio Board.

## Worktrees

**One workspace, many tasks; each task gets its own worktree.** Don't make copies of a workspace.

```
invoicer/
├── CLAUDE.md, .claude/, docs/       shared by all tasks
├── api/  web/  infra/               main checkouts, kept clean
└── .worktrees/                      git-ignored
    └── feat-billing/                one folder per task
        ├── api/                     branch feat-billing
        ├── web/                     branch feat-billing
        └── infra/                   branch feat-billing
```

**Why worktrees, not copies of the workspace**
- Knowledge and agent setup stay in one place. Copies would drift apart and overwrite each other.
- Each task's code stays separate.
- Registry, Improver and Global Index see one workspace, not several.

**Why inside the workspace**
- Agents pick up the workspace's `CLAUDE.md` automatically, since Claude Code also reads `CLAUDE.md` from the folders above.
- The Sandbox stays simple: agents never need anything outside the workspace.
- Everything for a task is in one folder.

**The Dispatcher manages worktrees, not the agents.** Claude Code's own `--worktree` handles one repo at a time; tasks can span several, so the Dispatcher runs `git worktree add` for each repo the plan names.

**Lifecycle**

| Event | Action |
|---|---|
| Task starts | Create `.worktrees/<task>/<repo>` for each repo in the plan, all on the same branch name |
| Agent runs | Starts inside `.worktrees/<task>/` and sees all its repos |
| Task blocked | Worktrees are kept, so the task can resume |
| All PRs merged or closed | Remove the worktrees and delete the branches |
| Nightly (Housekeeper) | `git worktree prune`; ask me about worktrees idle for more than 7 days |

Postgres records which worktrees belong to which task, so the dashboard can show them.

**A feature across several repos**
- **One issue** in the workspace repo describes the feature.
- **One PR per repo**, each linked to that issue.
- **Merge order** (e.g. infra → api → web) is set by the Lead in the plan.
- **Done means every PR is merged.** Only then are the worktrees removed.

**Caveats**
- **Running several copies of the app is the real cost.** Each worktree needs its own dependencies, ports and sometimes its own database. Give each task its own port range.
- **Shared docs.** Tasks don't edit `LOG.md` or the wiki while they run. Each writes a notes file for its task; the Improver merges the notes into the docs through one PR.
- **Limits.** A cap on how many worktrees exist at once, plus a disk-usage alert.

## Scheduler

**One Schedule List for every timed job.** The list is data the system owns; only the one-minute "tick" depends on the machine. Due entries go to the Dispatcher as normal tasks, so they get the same logging, token budget and alerts.

**Each entry**

| Field | Example |
|---|---|
| `when` | "every 30m", "daily 07:00", or once at a given time |
| `workspace` | `llm-evals` |
| `run` | A skill or prompt for an agent, or a script |
| `created_by` | The task, agent run, system or me |
| `until` | An end date, or a condition such as "runs finished" |
| `status` | Last run, next run, active or paused |

**Where entries live**
- System schedules: `ws-system/schedules.yaml`, changed through PRs.
- Schedules made by agents: rows in Postgres.

**Rules for agents**
- They create schedules through a skill.
- Every entry needs an owner and an `until`.
- I can list or stop any schedule from Slack.

**Background work is just schedule entries**

| Job | When | Owner |
|---|---|---|
| Planner | Daily | System |
| Improver | Daily | System |
| Housekeeper + Global Index | Nightly | System |
| Reports | Daily + weekly | System |
| Experiment check-ins | Every 30m | Its task; removed when the task is done |

## Runs

- Claude Code saves every session automatically to `~/.claude/projects/<path>/<session>.jsonl`. No extra folder is needed.
- **Claude Code deletes these logs after 30 days by default.** Raise `cleanupPeriodDays` to keep them longer.
- The Dispatcher writes one summary row per run to Postgres: workspace, task, status, tokens, summary, log path.
- Moving a workspace breaks the link to its past sessions. Another reason to register workspaces in place.

## Other flows

**Set up the system, add a workspace:** see [Setup Skill](#setup-skill).

**Improvement loop**
1. The Improver reads the Run Store daily.
2. It proposes fixes as PRs. I approve.
3. Generic wins go up to `ws-base` as PRs, and every workspace inherits them.
4. Check that it works: the failure rate falls over time.

**Publishing**
1. I add a `publish` label to an issue.
2. An agent drafts a post in `showcase/site` and opens a PR.
3. I merge, and the Automation Runner deploys the Showcase Site.

## Setup Skill

One skill, `workspace-os`, does both jobs. It lives in the Shared Skill Pack: `ws-base/plugin/skills/workspace-os/`.

| Command | Job |
|---|---|
| `/workspace-os setup` | Set up Workspace OS on a machine |
| `/workspace-os add <name> [path]` | Create a new workspace, or onboard an existing one |

**How the skill behaves**
- **Safe to re-run.** Checks each step and skips what's already done.
- **Plan first.** Shows what it will do, then asks before creating repos or changing system settings.
- **Never moves, overwrites or deletes** existing files. Conflicts become suggestions.
- **Never handles secrets.** It creates the Secrets Vault file; I fill it in.
- **Ends with a short report:** done, skipped, needs me.

**Bootstrap:** on a fresh machine, install the plugin from `ws-base` once, then run `/workspace-os setup`.

### Set up Workspace OS

1. **Check the Host:** Linux, git, `gh` (signed in), Claude Code, Python, Postgres.
2. **Create the root folder:** `~/workspace-os/`.
3. **Get the system repos:** clone `ws-base`, `ws-system` and `ws-index`, or create them if they don't exist yet.
4. **Write the settings:** `system/instance.yaml`, plus an empty Registry and Schedule List.
5. **Create the Secrets Vault:** `~/.config/workspace-os/env`, readable only by its owner. I fill in the tokens, including the Slack bot's.
6. **Configure Claude Code:** install the Shared Skill Pack; raise `cleanupPeriodDays`.
7. **Prepare the Host:** disable sleep, create the agent user, install the systemd units for the Dispatcher, Scheduler and Relay.
8. **Set up the Run Store:** create the Postgres database and tables.
9. **Set up Slack:** create `#hq`; check the Relay can read and post.
10. **Create the Portfolio Board** on GitHub Projects.
11. **Verify:** start the services, post a test message in `#hq`, report.

**Rebuilding a machine:** run `setup`. It reads the existing Registry and adds every workspace in it again.

### Add a workspace

The skill decides from the path: an existing folder is **onboarded**, a missing one is **created**.

1. **Name and path.** New workspaces default to `~/workspace-os/<name>`. Existing ones stay where they are.
2. **Lay down the structure.**
   - New: copy `base/template/`.
   - Existing: add only what's missing: `CLAUDE.md`, `.claude/agents/` (including the Lead), `docs/` (`ROADMAP.md`, `LOG.md`, `wiki/`). If a `CLAUDE.md` already exists, suggest changes instead of replacing it.
3. **List the repos.**
   - New: ask which repos to create or clone.
   - Existing: find the repos at the root.
   - Either way: write `repos.yaml` and add each repo to `.gitignore`.
4. **Create the workspace repo:** a private `ws-<name>` on GitHub; push the workspace files.
5. **Install the Shared Skill Pack.**
6. **Connect it to the system:**
   - Add it to the Registry (path, repo, channel).
   - Create its Slack channel and a "📊 Reports" thread.
   - Add its repos to the Portfolio Board.
   - Create the standard labels (`agent:ready`, `agent:running`, `needs:human`, `done`).
   - Add its daily Planner and Improver entries to the Schedule List.
7. **Verify:** the Dispatcher sees the workspace; the Lead answers a test message in the channel; report.

## Monitoring

**Index (Monitoring Console)**
- Tokens: day / week / month, per workspace and per agent
- Budget used %
- Agent runs: count, success rate, duration
- Issues opened / closed
- PRs opened / merged
- Workspaces active
- Items waiting on me
- Active schedules
- Agent idle time

**Drill-down:** Index → Agent runs → runs from the last few hours → summary, logs and PR for one run.

**Push vs pull**
- **Push** (Slack): alerts and decisions as DMs, reports in `#hq` and each workspace's Reports thread.
- **Pull** (Monitoring Console): browsing and digging into details.

## Reports

| Report | Where |
|---|---|
| Overall daily brief, Weekly Review | `#hq` |
| One workspace's daily and weekly updates | "📊 Reports" thread in its channel |
| Urgent: needs me now | DM |

Every report is also saved in `ws-index/reports/`.

**Weekly Review**
- Built from hard data: commits, merged PRs, closed issues, tokens used.
- Graded against each workspace's `ROADMAP.md`: done, slipped, blocked.
- Same template every week, so results can't be spun.

## Multiple instances

I'll run two separate copies of Workspace OS from the same code: one personal, one for my company's projects.

| | Personal | Company |
|---|---|---|
| Slack | My own free workspace | Company Slack |
| GitHub | My account | Company org |
| Machine | My Linux box | A company-approved machine |
| Secrets, Registry, Run Store, Global Index | Its own | Its own |
| `ws-system` code | Same | Same |
| `ws-base` skills | Personal copy | Company copy |

**Rules**
- **Settings, not hard-coding.** Everything specific to one copy lives in `system/instance.yaml`: Slack workspace, GitHub account or org, paths, token budget.
- **One-way sharing.** Generic improvements may go from personal `ws-base` to the company one. Nothing flows back: company code, data and lessons belong to the company.
- **The two never meet.** No shared index, reports or Slack.
- **Check company policy first:** allowed tools, where data may go, which Claude account pays.

## Reliability

| Risk | Fix |
|---|---|
| Machine sleeps | Mask the sleep targets in systemd |
| Crash or reboot | Supervisor restarts services; agents commit often and resume |
| Token limit | Dispatcher pauses until the reset, then resumes by priority |
| Network drop | Watchdog + retries; wired connection; a UPS if possible |
| RAM / CPU / disk | Concurrency cap, Sandbox limits, nightly cleanup |

## Guardrails

**Agents act freely on:** files in their workspace, Task Branches, staging.

**Agents need my approval for:** plans, merges to main, prod deploys, spending money, messages to other people, deletions.

**Token split (starting point):**
- Workspace work, including planning: about 70%
- Improver: about 15%
- Housekeeping: 15% at most

**Output contract:** at most 5 lines and at most one decision per message, given as options + a recommendation. Long content goes in files or issues; messages link to them.

## Build order

**v1 (only these):** Host, Registry, Setup Skill, Base Workspace, one Workspace with its Lead, Agent Runtime, Dispatcher, Supervisor, Task Tracker, Review Gate, Run Store, Slack + Relay.

Everything else is added when something actually hurts.

## Decisions made

| Question | Decision | Why |
|---|---|---|
| One shared base for all workspaces? | Yes: `ws-base` | Every workspace starts with all past learnings |
| Fork the base for new workspaces? | No: copy the template + install the plugin | Can't fork your own repo, and forks drift |
| A branch per workspace? | No: a repo per workspace | Branches are meant to merge back; workspaces need separate issues and access |
| What is a workspace? | A folder with its own small repo, holding several repos at its root | A project usually spans several repos |
| What does a workspace repo track? | Agent setup and knowledge, not the work itself | The work lives in the repos inside it |
| Several copies of a workspace for parallel tasks? | No: one workspace, a worktree per task in `.worktrees/` | Knowledge stays in one place; code stays separate |
| Who manages worktrees? | The Dispatcher | Tasks can span several repos; cleanup must be reliable |
| Nest repos with submodules? | No: `.gitignore` + `repos.yaml` | Simpler |
| Shared content and system code in one repo? | No: `ws-base` and `ws-system` | One gets copied into workspaces; the other runs once on the Host |
| Move existing workspaces under `workspace-os/`? | No: register them in place | Moving breaks session history and existing paths |
| How to set up the system and workspaces? | One `workspace-os` skill: `setup` and `add` | One entry point; safe to re-run; same steps every time |
| Registry contents | Path + workspace repo link + channel | Rebuild from GitHub; link tasks, activity and conversations to each workspace |
| Separate `runs/` folder? | No | Claude Code already saves session logs; Postgres holds the summaries |
| Main project-management tool? | GitHub Issues + Projects | Free, proven, agents know `gh`, issues link to code |
| Linear / Plane / Notion / Jira? | Not now | Not free or not proven enough; Notion is a weak task queue, Jira too heavy |
| Swap trackers later? | Agents reach the tracker through one skill | Changing trackers only means changing that skill |
| Interaction channel | Slack (my own free workspace) | Channels and threads map onto workspaces and tasks |
| Telegram? | Supported through the same Relay | Only the connection changes |
| A Notifier agent? | No: the Relay, plain code, both directions | Passing messages along needs no tokens |
| Who do I talk to? | The workspace's Lead; the HQ Agent for everything else | One voice per workspace, short and human |
